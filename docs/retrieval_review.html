The measuring stick

What a run actually produces

Every method here does one thing: take a question, score all 1,674 pages, sort them. NDCG@10 grades the top ten — a gold page at rank 2 is worth much more than the same page at rank 9, and anything past rank 10 scores zero. Recall@10 is the blunter companion: did any gold page make the top ten at all.

We measure on French only, the hardest slice of the hardest domain in ViDoRe V3. One caveat that runs through everything below: the internal ladder is quoted at NDCG@10, but the public ViDoRe V3 leaderboard uses NDCG@5, averaged over six languages. The internal deltas are all valid against each other; only the comparison to a leaderboard cell needs the metric aligned — done in the last section.

The pipeline · step by step

Baseline Legacy, walked through one query

“Baseline Legacy” is the text pipeline the results table is built on: pdf-inspector + KDL parse → fixed 512/128 chunks → text-embedding-3-small → hybrid BM25 + dense → MaxP → α-fuse. Here it is on a real question, with a real failure.

Query · physics::12

« Quelle gamme d'énergie en électronvolts correspond aux transitions moléculaires dans le spectre électromagnétique ? »

Which electronvolt energy range corresponds to molecular transitions in the electromagnetic spectrum? — gold answer: pages 24 and 32 of Les_2_infinis_Ch-2b-Quantique-Etats-Lies-Lasers
  1. 1

    Parse

    pdf-inspector finds the regions on each page; KDL reads the layout inside them. Output: clean text per page for all 1,674 pages. This is the stage that was just corrected — we had been on a plain-KDL parse; the CSV means pdf-inspector + KDL.

  2. 2

    Chunk

    Each page's text is cut into overlapping windows of 512 words, 128-word overlap. A page becomes one or more chunks; a chunk always knows which page it came from.

  3. 3

    Embed & index

    Every chunk is embedded with text-embedding-3-small (one 1,536-d vector) and also added to a BM25 keyword index. The query gets the same treatment.

  4. 4

    Search — two rankings

    BM25 returns chunks by keyword overlap; the dense index returns chunks by vector similarity. Two separate ranked lists of chunks.

    BM25 top hit: a chunk from Les_ondes_Ch-3 (“spectre électromagnétique” matches literally)
    dense top hit: a chunk from Les_ondes_Ch-3 too — both leaning toward the wrong book
  5. 5

    MaxP — chunks become pages

    Each page takes the score of its single best chunk. Now both lists are rankings of pages, not chunks.

  6. 6

    α-fuse → the pool

    Normalise both lists, then blend: 0.3 × BM25 + 0.7 × dense. Keep the top ~100. That's the pool every downstream arm re-orders.

    Pool for physics::12 — gold page 24 lands at rank 9, gold page 32 at rank 68.
    Ranks 1–5 are all Les_ondes_Ch-3 and L_energie_Ch-1 — wrong books, sitting above the gold.

The failure signature

The pool almost always contains the gold page — recall into the top 100 is ~98%. The problem is the ordering inside it. In roughly 69% of the misses the right document is already in the top 10, but the wrong pages of it rank first, and a handful of pages from neighbouring chapters slip above the gold. physics::12 is exactly this: the right book is represented (page 24 at rank 9), but its two gold pages aren't ranked together and four wrong-book pages sit on top. Every arm below is an attempt to fix that one thing.

Read across the table and one pattern holds

Every arm fixes the same failure — right book, wrong page. So they don't add up. Whichever single strong lever you apply, the others have little left to correct. The big jump was never a clever combination; it was making one component genuinely better: ColQwen2-2B → ColVec-8B, +5.9 from the model alone. The visual reader was the bottleneck the whole time.

The one lever on a different axis entirely: swapping the answer generator (DeepSeek-V4-Flash → GPT-5.2) moved end-to-end answer accuracy +27.7 points — about 20× the entire retrieval ladder. Retrieval and generation are separate dials; almost all the headroom is on the other one.

A common question

Why the parser fix needed no GPU re-run

The pipeline is two independent halves that meet only at the end, joined by page number. The parser lives in one of them.

Text arm

the parser feeds this
  1. PDF → parse (pdf-inspector + KDL)
  2. page text → chunk
  3. embed + BM25 index
  4. search → MaxP → α-fuse
  5. pool: {page → text score}

Visual arm

the parser never touches this
  1. PDF → render page to a PNG
  2. image → ColVec model
  3. page multi-vector
  4. MaxSim vs query
  5. {page → visual score}
0.2 × text score[page]  +  0.8 × visual score[page]  →  final rank

Rendering a page to an image rasterises the PDF's actual content — it doesn't read what the parser extracted. So the ColVec score for a page is identical no matter how (or whether) we parsed. When the parse was corrected, what re-ran was the text arm (local, ~3 min, cached embeddings) and the fusion arithmetic (instant). The 302×1,674 ColVec score matrix from the Colab run is still exactly valid — the 53.15 number is that re-run: the new text pool fused with the untouched visual matrix.

The only reason to touch a GPU again is a genuinely new visual experiment (below), or to regenerate the matrix from scratch if it's ever lost — which is why the notebook was ported to Kaggle, not because anything broke.

The last experiment

Metarank — what it is and why it didn't help

Metarank is an open-source ranking service. Its model is LambdaMART — a gradient-boosted tree ranker — plus a feature store and an HTTP server. It is not a cross-encoder: it never reads query and page text together. It re-orders using numeric features you give it, and normally learns from a click stream.

What we did

We have no clicks, so we used the benchmark's own relevance labels. Each query became one “ranking event” carrying its ~100 pool pages, each page tagged with 17 features (the component scores, the SEP signals, the ColVec score, ranks, page number, same-book count, query length) and its gold grade. We ran the real Metarank 0.8 JAR — metarank standalone → XGBoost backend, its own 80/20 split — and, in parallel, the same LambdaMART core directly with proper 5-fold cross-validation.

The result

51.14
LambdaMART · 5-fold held-out
53.15
the hand-tuned SEP + ColVec blend
+8.60
oracle per-query headroom · still locked

The learned ranker reproduces the hand-tuned blend and no more — 51.1 is within noise of the fixed 53.2, slightly under. Its single most-used feature, by a wide margin, is the SEP book-level score. It re-derived “trust SEP + trust ColVec” — the rule we already wrote by hand. It did not find a per-query strategy (“for this kind of question trust the text, for that kind trust the picture”).

That matters because we know an oracle picking the perfect text-vs-visual weight per query would gain +8.6 — the largest unexploited number in the whole project. Three separate attempts have now confirmed there is no signal in the features that predicts, per query, how to combine the arms. Closing that gap needs something we don't have: real user click data, or a much stronger judge model. Metarank's value here is serving latency (microseconds per query), not the score.

Sanity check

Does this match the leaderboard?

A fair question — the ViDoRe V3 leaderboard shows webAI-ColVec at 0.4851 on physics, below our 53.15. Three things differ, and aligning them makes the numbers agree.

  • Metric. ViDoRe V3's primary score is NDCG@5, not @10. Our whole ladder was quoted at @10 — self-consistent, but one cutoff higher than the leaderboard.
  • Language. The leaderboard column is a 6-language average; we run French only, which is consistently the harder half (FinanceFr 0.54 vs FinanceEn 0.68).
  • System. Our 53.15 is a pipeline number — text pool + SEP + visual fusion — not a standalone model.

Align them: our ColVec visual-only at NDCG@5 = 47.84 (French), against the leaderboard's 48.51 (6-language). Gap 0.7, all of it language. Same 1,674-page corpus, same gold labels (962/962 present), same scoring library MTEB uses. The eval reproduces the leaderboard. The pool-restriction worry also dissolves — 48.17 vs 47.84 is nothing.

What it means: we are at leaderboard level, not past it. The “past SOTA” framing came from comparing our @10 to a @5 board. ViDoRe V3 overall SOTA is ~57–59 NDCG@5; physics is the floor at ~48–51; “~60” on physics-French is well beyond anything reported.

The call

Freeze retrieval. Move to the answer axis.

SEP + ColVec-8B sits at leaderboard level for this domain (NDCG@5 47.8 standalone, 49.8 as a pipeline), and every retrieval lever now fixes the same 69% failure — they've stopped stacking, proven on SEP, ColQwen2, two cross-encoders, and a learned combiner. The one lever left (more visual tokens) is a maybe. Meanwhile the generator swap moved end-to-end answer accuracy +27.7 points, and that number is unmeasured on the current retrieval stack. The ceiling is not where we've been digging.

Do next

Measure end-to-end QA on SEP + ColVec top-10

Run Correct_only / Correct+partial with a strong generator on the current stack. This is the number the pipeline actually delivers to a user, and we've never measured it on anything better than the raw baseline.

Parallel · cheap

ColVec at max_visual_tokens = 3584

The one retrieval lever left. At 144 DPI the model already downscales every page to its 1,792-token budget, so more DPI does nothing — but doubling the token budget gives it finer patches to read equations with. One overnight Kaggle run; notebook is ready. Only pursue if it beats 53.15 by more than ~0.7.

Don't

Voyage-on-KDL · more fusion permutations · tuning LambdaMART

A cross-encoder on top of ColVec hurts. Stacking is redundant — shown three times. LambdaMART lands on the blend. All three spend effort where the evidence says there's nothing left.
